# 설계 문서 검증 (design-verify)

설계 문서를 3단계로 검증하고, 발견 사항을 심각도(구조 충돌 > 문서 결함 > 구현 갭 > 사소)순으로 보고한다.
"통과"만 나열하지 말고 반드시 반례를 찾으려는 태도로 접근한다.

## 1단계 — 구문 검증 (기계 검증)

- 문서의 모든 ```mermaid 블록을 추출해 `npx -y @mermaid-js/mermaid-cli -i <f> -o <f>.svg`로 실제 렌더링한다. 눈으로 읽는 것만으로 통과시키지 않는다.
- 깨진 외부 참조를 찾는다: 이미지/첨부(`!file`, `.svg`, `.png`)가 repo에 실재하는지, 외부 링크(mermaid.ai, Notion)만으로 존재하는 원본이 있는지. **정본 문서의 원본이 repo 밖에만 있으면 결함이다.**
- 내보내기 잔재를 찾는다: `‣`, 빈 placeholder, 끊긴 상대 링크.

## 2단계 — 의미 검증 (다이어그램 내부·상호)

**상태도(stateDiagram)마다:**
- 모든 상태에 진입 경로와 탈출 경로(또는 명시적 종료)가 있는가 — 고아 상태, 막다른 상태를 찾는다.
- 실패·타임아웃 경로가 있는가 (해피패스만 그려진 상태도는 미완성).
- 문서 본문이 서술한 전이가 다이어그램에 전부 있는가, 다이어그램에만 있고 본문에 없는 전이는 없는가.

**시퀀스/플로우차트마다:**
- 분기(diamond)의 모든 가지가 종결되는가.
- 실패 시 자원 정리(업로드 롤백, 락 해제)가 그려져 있는가.
- 동시성 서술(락, 버전 체크)이 실제로 경합을 막는 순서인가.

**다이어그램 상호:**
- 같은 개념이 다이어그램마다 같은 이름·같은 상태 집합으로 등장하는가.
- 결과/상태 열거표(예: 검증 결과 표)와 판정 플로우차트의 출력 집합이 **정확히 일치**하는가 — 표에만 있는 상태, 플로우에만 있는 상태를 대조한다.
- 엔터티 목록·테이블 개수 주장(예: "16개")을 실제로 세어 검증한다.

**ERD 자체:**
- 관계선의 카디널리티가 본문 제약 서술과 일치하는가.
- "DB 제약으로 막을 것" 목록의 각 항목이 유니크/FK/CHECK로 표현 가능한가, 다형성 FK는 타입별 배타 제약이 명시됐는가.

## 3단계 — 구현 정합성 (코드 대조)

- 문서의 각 테이블/컬럼/제약을 `src/main/java/**/entity/*.java`와 대조한다: 엔티티 존재 여부, `@UniqueConstraint` 컬럼 조합, enum 상태 집합, nullable 여부.
- **문서에서 사라진 엔터티가 코드에 남아있는 것**(폐기 누락)과 **문서가 요구하는 제약이 코드에 없는 것**(구현 갭)을 구분해 보고한다.
- 문서의 API 경로 규약(버전 prefix, publicId 사용)과 실제 컨트롤러 매핑을 대조한다.

## 보고 형식

1. 한 줄 판정 (통과/조건부/반려 + 핵심 사유)
2. 구조 충돌 (설계끼리 또는 설계-구현이 모순 — 결정 필요)
3. 문서 결함 (깨진 참조, 카운트 불일치, 표-플로우 불일치)
4. 구현 갭 (문서 요구사항 중 코드 미반영 — 조치 목록화)
5. 확인된 정합 항목 (간략히)
