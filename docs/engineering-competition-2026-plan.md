# Trekkey 공학경진대회 제안·시연·검증 계획

## 1. 작품 제목

**Trekkey: Merkle Proof 기반 개인정보 보호형 대학 활동 Credential 발급·검증 플랫폼**

제목에서 설명하는 실제 범위는 다음과 같다.

- **Trekkey Protocol**: 활동 증거를 표준화하고, 해시·Merkle Proof·서명·상태 이력으로 검증하는 규칙
- **Trekkey Platform**: 발급 기관, 신청자, 심사자, 검증자와 블록체인을 연결하는 운영 기반
- **Trekkey Services**: 대회 운영, 활동 프로필, 공개 검증, 향후 연결될 졸업요건 등 사용자 서비스
- **Trekkey Network**: 향후 복수 대학·기관이 발급자로 참여할 수 있는 federation-ready 지향 구조

> 현재 실증 범위는 단일 대학 서비스와 Kaia Kairos 테스트넷이다. 완성된 다기관 탈중앙 네트워크로 표현하지 않는다.

## 2. 작품 개요

생성형 AI의 보급으로 자기소개서와 포트폴리오를 쉽게 작성할 수 있게 되었지만, 그 안의 활동 경험이 실제로 인정된 사실인지 외부에서 판단하기는 더 어려워졌다. 구직자는 자신의 실제 경험을 설득력 있게 증명하기 어렵고, 기업은 지원서의 서술만으로 검증된 역량을 구별하는 데 많은 비용을 지불한다.

Trekkey는 대학·기관이 승인한 대회 참여, 수상, 팀 작품 등의 활동 증거를 Credential로 발급한다. 개인정보와 원문은 블록체인에 올리지 않고, 복수 Credential의 Merkle Root와 상태 이력만 공개 원장에 기록한다. 외부 검증자는 개별 Credential의 Merkle Proof와 기관 서명, 현재 취소·정정 상태를 확인해 제시된 증거가 기관이 발급한 배치에 포함되었고 이후 변조되지 않았는지 판별할 수 있다.

Trekkey의 핵심은 모든 정보를 블록체인에 공개하는 것이 아니라, **필요한 정보는 서비스에서 전달하고 무결성 판단에 필요한 최소 증거만 공개 원장으로 확인하는 것**이다.

## 3. 작품의 주요 기능

### 3.1 대학 활동 운영·승인

- 대회 개설, 팀 구성, 작품 제출, 심사, 수상 결과를 하나의 이력으로 관리한다.
- 권한별 승인 절차를 통과한 활동만 Credential 발급 대상이 된다.
- 평가위원 전용 접근 경로와 운영자 상태 관리를 분리한다.

### 3.2 표준 Credential 발급

- 참여, 작품, 수상 등 서로 다른 활동을 공통 발급 파이프라인으로 변환한다.
- JSON 정규화, SHA-256/Keccak 해시, EIP-712 기관 서명을 생성한다.
- 원문 변조 또는 필드 순서·유니코드 표현 차이가 검증에 미치는 영향을 일관된 규칙으로 처리한다.

### 3.3 Merkle Proof 기반 일괄 앵커링

- 복수 Credential의 해시로 Merkle Tree를 구성하고 Root만 한 번에 온체인 기록한다.
- 각 Credential은 전체 배치를 공개하지 않고도 자신이 배치에 포함되었음을 Proof로 검증할 수 있다.
- 리레이 실패를 재처리하고 온체인 read-back으로 최종 성공을 확인한다.

### 3.4 공개 검증·활동 프로필

- QR 또는 공개 ID로 기관, 활동 요약, 발급 상태, 블록체인 증거를 확인한다.
- 이메일, 학번, 내부 사용자 ID 등은 공개 프로필에 노출하지 않는다.
- 공개 검증 ZIP은 공개 요약, Proof, 앵커, 기관 승인, 상태, 증명서 PDF만 포함한다. 개인 원문은 포함하지 않는다.

### 3.5 취소·정정 이력

- 오발급이나 사실관계 변경 시 Credential을 취소하거나 새 Credential로 대체한다.
- 검증자는 과거 문서의 존재뿐 아니라 현재 유효성과 정정 계보를 확인한다.

### 3.6 Tamper Lab

- 시연용 Credential의 이름, 결과, 날짜 중 한 필드를 의도적으로 바꿔 해시·Merkle Proof 검증 실패를 보여준다.
- 유효한 증거, 변조된 증거, 취소된 증거, 정정된 증거의 결과를 한 화면에서 비교한다.
- 심사자가 기술의 필요성과 검증 결과를 즉시 이해하게 하는 핵심 시연 장치다.

## 4. 현재 개발 상황

해당 작품은 기존 Trekkey 대회 관리 서비스를 Credential 발급·검증 프로토콜과 플랫폼으로 확장해 출품하는 것을 목표로 한다.

현재 구현된 범위는 다음과 같다.

- 대회·팀·작품·심사·수상 운영 흐름
- 참여·작품·수상 Credential 발급 adapter와 공통 발급 파이프라인
- canonical JSON, SHA-256, Keccak, OpenZeppelin 호환 Merkle Proof, EIP-712 서명
- Kaia Kairos 기반 배치 앵커링, 재처리, read-back, 취소·정정
- 공개 Credential 검증, 신뢰 요약, QR, 공개 활동 프로필
- 관리자·참가자·평가위원 별 웹 화면
- Java 서버 자동화 테스트 629개와 Solidity 테스트 12개

## 5. 작업 중인 개선 사항

### P0 — 본선 시연에 필수

- 동일한 seed data로 반복 가능한 `발급 → 앵커 → 검증 → 변조 감지 → 정정/취소` 시연 구성
- Tamper Lab UI와 성공·실패 원인 설명
- Vercel·API 배포 환경의 인증 라우팅 분리와 배포 전 smoke test
- 시연 화면의 동작하지 않는 제어 제거 및 서버 상태와 UI 상태 일치
- 발급, 앵커, 검증, 취소·정정 흐름의 시연 체크리스트와 장애 대체 영상 준비

### P1 — 기술적 완성도

- 배치 크기별 가스, 대기 시간, 처리량 벤치마크
- RPC 장애, transaction timeout, 중복 이벤트 주입 테스트와 회복 시간 측정
- 발급자 키 교체·폐기·탈취 상태 시나리오
- 현재 `user:{DB id}` 형식인 사용자 subject reference를 별도의 불변 opaque public ID로 마이그레이션
- 발급자 조직의 `publicId` 필수 제약·backfill으로 대외 식별자 일관성 확보
- 관리자 블록체인 변경 명령의 service-layer 현재 권한 재검증과 감사 이력 강화
- 앵커 outbox backlog, 오류율, 최종 성공 지연에 대한 지표·readiness 구성
- 로컬 파일 저장소를 운영용 object storage로 전환

### P2 — 플랫폼 확장

- 복수 대학·기관의 발급자 등록, 정책, 스키마 버전 관리
- Credential 소유자 본인에게만 제공하는 전체 portable package 및 소유권 확인 경계
- 필드 단위 selective disclosure와 영지식증명 적용 가능성 연구
- 취소·정정 변경을 지속 확인하는 검증자 알림 서비스

## 8. 졸업요건 팀 연동 계약

졸업요건 기능의 소유·개발은 별도 팀에 있다. 본 작업에서는 해당 도메인을 구현하거나 DB를 변경하지 않고, Trekkey 연동 경계만 정의한다.

### 역할 분리

- **졸업요건 서비스**: 학생·교과·자격증·요건 정책 정보를 관리하고 달성 판정의 근거를 생성한다.
- **기관 승인자**: 판정 결과와 근거의 최종 발급 여부를 승인한다.
- **Trekkey**: 승인된 결과를 공통 Credential 명령으로 받아 정규화, 서명, 배치, 앵커링, 상태 관리, 공개 검증을 담당한다.

### 입력 계약

졸업요건 팀은 백엔드 내부 adapter를 통해 `CredentialIssuanceService.issue(CredentialIssueCommand)`를 호출한다. 웹 브라우저나 외부 서비스가 온체인 함수를 직접 호출하지 않는다.

필수 개념 필드:

- `requestId`: 멱등적 재시도를 위한 요청 ID
- `credentialType`: 향후 합의할 `GRADUATION` 유형
- `sourceType`, `sourcePublicId`, `sourceVersion`: 발급 근거의 출처와 버전
- `subjectPublicId`: 로컬 DB 숫자 ID·학번·이메일이 아닌 대외용 opaque ID
- `claims`: 승인 결과, 기준 버전, 판정 일시, 근거 요약
- `evidenceRefs`: 필요한 경우에만 사용하는 내부 근거 참조
- `approvedBy`, `approvedAt`: 기관 승인 주체와 시각
- `schemaVersion`, `policyVersion`: 재현 가능한 스키마·정책 버전

### 보안·정합성 원칙

- 학번, 이메일, 성적 원문, 증빙 파일은 온체인 필드와 공개 subject reference에 넣지 않는다.
- Credential hash를 브라우저가 생성해 전달하지 않고, Trekkey 서버가 정규화된 패이로드로 생성한다.
- 출처 데이터가 변경되면 기존 Credential을 덮어쓰지 않고 취소 또는 정정 계보를 생성한다.
- 연동 테스트는 가상 graduation fixture와 adapter contract test로 수행하며, 다른 팀의 데이터베이스를 직접 수정하지 않는다.

### 사용자 서비스 연결

졸업요건 조회는 참가자 활동 프로필·결과·이력 화면에 별도 카드로 연결한다. 대회 Credential 스키마에 졸업 정보를 무리하게 넣지 않고, 프로토콜의 공통 발급 규칙을 공유하는 독립 Credential 유형으로 설계한다.

## 10. 정확한 기술 표현

발표·포스터·문서에서 다음 경계를 유지한다.

- Merkle Proof는 배치 포함과 무결성을 검증하지만 영지식증명은 아니다.
- 블록체인은 기록 후 변조 여부와 상태 이력을 검증하지만, 기관이 입력한 현실 세계 사실 자체를 자동 판정하지는 않는다.
- 개인정보 보호는 원문 온체인 미저장, 공개 필드 최소화, opaque ID, 접근 경계로 설명한다.
- 현재는 Kaia Kairos에서 검증하며 메인넷 운영 성과로 포장하지 않는다.
- 현재 구현과 향후 설계 목표를 슬라이드와 시연에서 명확히 구분한다.
